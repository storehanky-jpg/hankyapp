# Project memory

## Product intent & audience

- App for generating and managing business documents: invoices (`facture`) and vouchers/credit notes (`bon`).
- Documents are persisted with their full HTML rendering, totals, customer info, and billing period.
- UI language: French.

## Brand personality & voice

- Production-grade, beautiful, non-cookie-cutter UI (per `.bolt/prompt`).
- Assistant communicates in French.

## Visual design & UX direction

- Stack: Vite + React (JSX), Tailwind CSS, Lucide React icons; no extra UI/theme/icon packages unless explicitly requested (per `.bolt/prompt`).
- Expected upcoming: screens to list/view `documents` (invoices and bons) generated by the app.

## Decisions, constraints & rationale

- Supabase is the database/backend.
- `documents` table: `id` (uuid PK, `gen_random_uuid()`), `doc_type` text NOT NULL (`facture`|`bon`), `number` int NOT NULL, `doc_date` date NOT NULL, `customer_id` text, `customer_name` text, `period_from` date, `period_to` date, `total` numeric, `html` text, `created_at` timestamptz default `now()`.
- RLS enabled on `documents` with 4 open policies (select/insert/update/delete) for `anon` and `authenticated`, intentionally mirroring `orders` (open access).
- Reference table `orders` exists with the same open policy pattern; use it as the model for future tables.
- Migrations are applied to the live DB; code files are intentionally left untouched unless requested.
- App does not yet use the `documents` table; wiring into screens is a pending next step.

## Open questions & assumptions

- When/how to surface `documents` in the UI (list view, per-document HTML preview, printing/export) is undecided.
- Numbering scheme for `number` (auto-increment per doc_type vs manual) not yet specified.
- Whether `customer_id` references another table or is free text is unconfirmed.
- Open RLS is permissive for development; production auth/row policies may need tightening later.
